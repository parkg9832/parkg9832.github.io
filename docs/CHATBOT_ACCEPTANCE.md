# MOKDA 챗봇 완료 기준

작성일: 2026-10-11. 이 문서는 새 챗봇 목표에 대한 검수 기준이며, 현재 구현이 이미 통과했다는 뜻은 아니다.

## 이번 배포 범위

대표님의 2026-10-11 최신 지시에 따라 AI 서버 없이 상담창·공개 정보 자동 안내·공식 WhatsApp 연결을 먼저 배포한다. 흰색/차콜 시안은 같은 날 명시적으로 승인받았다. 아래의 광범위한 대화 평가 코퍼스는 추가 발전을 위한 진단 자료이며 모든 자유문장 이해 항목을 통과했다는 주장은 하지 않는다. 이번 단계의 필수 검증은 공개 14개 안내 영역, 세 언어, 제품/국가/수량 정정, 복수 알려진 질문, 담당자 연결, 입력 포커스, 페이지 간 대화 유지, 대기 답변 취소, 접근 가능한 패널과 안전한 텍스트/링크 처리다. 생성형 AI와 WhatsApp 계정 내부 AI 자동응답은 활성화하지 않는다.

## 목표와 범위

방문자가 우측 하단 원형 버튼에서 대화를 시작하고, 제품·활용법·구매·상업 조건·브랜드·소식·협업·수출 문의를 자연스럽게 이어갈 수 있어야 한다. 고급 상담 서비스 수준의 정돈된 말풍선·입력창·선택지·모션을 데스크톱과 모바일에 구현하고, 검증 후 커밋·푸시·공개 배포까지 완료한다. 이번 사용자 지시에 따라 챗봇의 시각 디자인은 기존 브랜드 색상에 묶이지 않는다.

기능은 공개된 MOKDA 지식과 담당자 연결을 중심으로 한다. 다른 주제의 일반 지능, 고객 주문·결제 조회, 아직 연결하지 않은 WhatsApp AI 수신·발신 서버를 구현된 기능처럼 보여주지 않는다. 홈페이지 챗봇과 WhatsApp Business 계정 내부 자동응답은 다른 운영 범위다.

## 현재 코드에서 확인한 간극

2026-10-11의 `site-chat-intents.js`는 한 입력을 14개 FAQ 답변 ID 중 하나로 연결한다. `site-help.js`의 `context`에는 최근 문의 문자열만 남아 있으며 제품·국가·수량·취향·목적을 구조적으로 보존하지 않는다. 같은 페이지에서 말풍선이 남는 것과 이전 발화의 의미를 이해하는 것은 서로 다른 기능이다.

직접 실행한 기존 matcher 결과는 다음과 같다.

| 입력 | 기존 결과 | 검수상 의미 |
| --- | --- | --- |
| Estoy en Lima | null | 구매 흐름에서 국가·도시 답변을 받지 못함 |
| ¿Y cuánto cuesta esa? | pricing | 가격 유형만 인식하고 esa의 제품 문맥은 받지 못함 |
| ¿Con tacos? | null | 자연스러운 음식 활용 후속 질문을 놓침 |
| La otra | null | 두 제품 사이의 대명사 전환을 놓침 |
| 타코랑 먹어도 되나요? | ingredients | 일반적인 음식 활용 질문을 알레르겐 질문으로 잘못 연결 |
| 가격이랑 개봉 후 보관을 알려줘 | null | 알려진 두 요청을 함께 처리하지 못함 |
| Does the other one have milk? | null | 제품 대명사와 구체적 알레르겐 질문을 놓침 |

기존 `scripts/chat-intents.test.mjs`의 42개 공개 질문 확인은 같은 문장을 해당 FAQ ID에 연결하는 증거다. 기존 `scripts/help-regression.test.mjs`의 답변 동일성·링크·위젯 수명주기·입력 안전 검사는 유지할 가치가 있지만, 복수턴 상담 성능이나 고급 UI 품질의 증거로 확대 해석할 수 없다. 특히 ‘타코랑 먹어도 되나요?’를 ingredients로 기대하는 기존 검사는 고객 의도와 어긋난다.

## 대화 성능

1. 문장의 실제 목적에 답한다. 가격을 묻는 사람에게 브랜드 소개를 먼저 읽게 하지 않고, 음식 조합을 묻는 사람에게 알레르겐 문단만 제공하지 않는다. 부정 표현·짧은 문장·일반적인 오타·발음 표기·악센트를 다룬다.
2. 제품·국가·도시·수량·업종·판매 채널·문의 목적·맛 선호를 대화 중 기억한다. 이미 받은 정보를 다시 묻지 않으며, ‘그거/다른 거/esa/the other one’은 가까운 제품 문맥으로 해석한다. 불확실하면 한 번 짧게 확인한다.
3. 수정 발화를 적용한다. ‘페루가 아니라 멕시코’, ‘100병 말고 10병’, ‘다른 소스’는 기존 사실을 대체한다. 이전 값과 새 값을 모두 현재 주문으로 요약하지 않는다.
4. 한 문장에 두 질문이 있으면 알려진 답을 각각 짧게 제공하거나 필요한 한 가지 확인을 한다. 모든 요청을 일반적인 ‘답변이 없습니다’로 버리지 않는다.
5. 한 차례 답변은 핵심을 먼저 1~3문장으로 제공하고, 필요한 링크·짧은 선택지를 함께 둔다. 대화 흐름은 가능한 한 3회 이내의 질문·선택으로 답 또는 담당자 연결에 도달한다. 일반적인 질문마다 메뉴를 다시 시작하지 않는다.
6. 한국어·중립 LATAM 스페인어·영어에서 동일한 사실·행동을 유지한다. 현재 페이지와 다른 언어 입력도 이해하고, 방문자의 명시적 답변 언어 변경을 기존 문맥을 유지하며 반영한다.
7. 인사·감사는 짧게 받되 마지막 실질 문의를 덮어쓰지 않는다. 실제 상담원이 들어와 있거나 읽는 중인 것처럼 가장하지 않는다.

## 사실과 안전 경계

- 현재 공개 제품은 K-PEÑO와 Para Carnes 두 가지다. 과거 문서에 Ganjang이 있어도 현재 공개 판매 제품으로 추가하지 않는다.
- K-PEÑO는 고추장·할라피뇨 기반의 매콤한 소스다. Para Carnes는 쌈장 기반이며 익힌 고기·채소에 곁들이는 용도가 공개되어 있다. Para Carnes를 무조건 무매운 소스라고 단정하지 않는다.
- 제품 소개의 알레르겐은 K-PEÑO 우유·대두·밀·토마토, Para Carnes 대두·밀이며 Para Carnes 레시피에는 참깨·참기름이 포함된다. 전체 최신 패키지 표시가 우선이다. 소개에 특정 성분이 없다는 사실을 해당 성분의 완전 무함유·교차접촉 없음으로 바꾸지 않는다.
- 개봉 전 상온·개봉 후 냉장이라는 소개 안내를 사용할 수 있지만, 개봉 후 보관 일수·소비기한·냉동 검증 결과를 만들지 않는다. 실제 패키지의 안내와 날짜를 확인한다.
- 가격·판매처·재고·최소 주문량·샘플·배송·독점권·인증·수입 허가는 현재 공개 확인 정보가 없으면 담당자 확인 대상으로 남긴다. 식품 알레르기·임신 등 개인의 섭취 안전을 보증하지 않는다.
- 언론·행사 답변의 제목·날짜·내용은 현재 `site-news-data.js`와 해당 공개 상세 페이지를 근거로 한다. KOTRA 미팅·언론 언급을 판매 계약·공식 보증으로 확대하지 않는다.
- 방문자가 거짓 가격·인증을 요구해도 사실 경계를 지킨다. HTML·스크립트·키 요청은 실행·노출하지 않으며 주문·결제·외부 발송이 실제로 일어나지 않았다면 성공을 주장하지 않는다.

## 담당자와 WhatsApp 전환

공식 번호는 `site-contact-config.js`를 단일 기준으로 사용한다. 번호를 테스트 코드나 이 문서의 별도 운영 상수로 복제하지 않는다.

‘담당자/사람/WhatsApp으로 상담’ 요청에는 추가 메뉴나 개인정보 입력 절차 없이 바로 연결한다. 버튼을 직접 누르면 문의 목적·현재 제품·국가·수량·채널과 마지막 미해결 질문을 포함한 간단한 초안을 만든다. 수정된 값은 이전 값을 대체하며 인사·감사가 문의 요약을 덮어쓰지 않는다. 초안은 고객이 WhatsApp에서 직접 전송한다. 자동 발송·웹사이트 실시간 상담원 입장·계정 내부 AI 활성화를 암시하지 않는다.

잘못되거나 비어 있는 번호, WhatsApp을 사용하지 않는 방문자에게는 실제 작동하는 언어별 문의 페이지를 제공한다. 전체 대화·민감 정보·불필요한 브라우저 데이터를 외부 메시지에 무제한으로 넣지 않는다. 실제 고객에게 시험 메시지를 보내거나 문의 양식을 제출하지 않는다.

## 디자인과 인터랙션

- 최소 3개의 실제 고객상담 서비스 레퍼런스를 브라우저에서 직접 보고, 출처·날짜·스크린샷·채택한 패턴을 남긴다. 검색 결과나 홍보 문구만으로 눈으로 확인했다고 주장하지 않는다. 템플릿이 적합하면 라이선스와 현재 정적 사이트의 통합 비용을 확인한 뒤 사용한다.
- 데스크톱은 우측 하단 원형 버튼과 화면을 과하게 덮지 않는 정돈된 패널을 사용한다. 인사·메시지·짧은 제안·입력·보내기·닫기·담당자 링크의 위계를 분명히 한다. 과도한 선택지, 모든 문장의 장문 버튼, 원문 FAQ 창 같은 형태를 피한다.
- 모바일은 320·390·430px에서 긴 메시지와 키보드가 열린 상태까지 확인한다. 입력창·닫기·전송·담당자 연결을 가리지 않는다. 입력 글자 16px 이상, 주요 탭 대상 44px 이상, safe area와 짧은 가로 화면 대응을 유지한다.
- 텍스트를 한 글자씩 오래 늘어놓기보다 짧은 말풍선 그룹으로 읽히게 한다. 열기·닫기·메시지 등장·자동응답 처리 표시·버튼 피드백에는 절제된 모션을 적용한다. 실제 자동응답 처리 중인 상태만 표시하고 사람이 입력하는 것처럼 꾸미지 않는다.
- `prefers-reduced-motion`에서는 불필요한 이동·확대·반복 모션을 제거한다. 입력과 활성 메시지가 흔들리거나 레이아웃이 튀지 않는다.
- 키보드·스크린리더·포커스 이동·한국어 IME Enter를 실제 브라우저에서 확인한다. JSDOM 폴리필의 성공을 네이티브 대화창·소프트웨어 키보드 증거로 쓰지 않는다.

## 시스템 선택

생성형·semantic API 자체는 목표의 필수 기술이 아니다. 다만 현재의 무문맥 키워드 → 긴 FAQ 문단 구조만으로는 목표가 충족되지 않는다. 좁은 MOKDA 도메인에서 문맥 상태·제품 엔티티·복수 의도·정정·질문 흐름을 갖춘 로컬 엔진이 독립 벤치마크와 처음 보는 유사 문장을 통과하면 비용 없는 방식으로도 요구를 달성할 수 있다.

폭넓은 자유문장 이해·복잡한 질의 합성·지식자료 자동 갱신까지 기대할 경우, 근거가 제한된 검색/semantic 응답 서버가 더 적합하다. 그 경우 검증된 지식만 전달하고 공개 클라이언트에 API 키를 넣지 않으며 실제 운영 연결·권한·비용을 확인해야 한다. API 연결 전 목업 응답을 실제 AI 성능으로 표시하지 않는다.

로컬 fallback은 API 실패 시에도 제품 기본 안내·가격/알레르겐의 사실 경계·담당자 연결을 제공하는 역할을 맡는다. 서버가 없거나 timeout·429·500·잘못된 결과·오프라인이면 짧은 안내와 문의 초안을 보존한 연결을 제공하며, 끝나지 않는 처리 표시나 재입력 요구를 만들지 않는다.

## 검증 자료와 통과 판단

독립 대화 코퍼스: `output/chat-redesign/quality-scenarios.json`. 현재 48개 복수턴 시나리오와 10개 UI·수명주기·오류·배포 기준이 들어 있다. 각 시나리오 내에서는 상태를 초기화하지 않고 실제 대화를 이어가며, 발화별 실제 응답·문맥·문의 초안·답변 근거·판정 이유를 저장한다. 이를 엔진에 그대로 하드코딩해 통과시키지 않는다. 각 언어와 문의 분야의 처음 보는 표현도 추가 검수한다.
