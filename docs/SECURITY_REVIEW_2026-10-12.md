## 2. 유지하고 검증하는 방어

- 정적 페이지: `scripts/static-security.mjs:12`의 메타 CSP는 `object-src 'none'`, `frame-src 'none'`, `form-action 'none'`, `script-src-attr 'none'`을 적용한다. 스크립트에 `unsafe-inline`·`unsafe-eval`을 허용하지 않는다. 문의/AI/분석 연결 목적지를 제한하며 AI 연결은 정확한 MOKDA Worker 출처만 허용한다. 현재 반응형 스타일 때문에 인라인 CSS는 허용한다.
- AI 요청: `workers/mokda-chat/src/index.js:4`부터 정확한 출처 허용 목록, JSON 콘텐츠 형식, 12,000바이트 스트리밍 본문 상한, 메서드 검사를 적용한다. 사용자 메시지 수·길이와 엔티티는 서버에서 다시 검사한다. 브라우저의 역할/값을 그대로 시스템 권한으로 사용하지 않는다.
- AI 비용/남용: `workers/mokda-chat/src/limiter.js`의 단일 Durable Object에서 원자적으로 하루 최대 80회, 같은 방문 IP 기준 분당 3회·하루 20회를 예약한다. 제한 장치가 없거나 실패하면 AI를 호출하지 않는다. 실패한 모델 요청도 예약을 소비한다. 출처 검사는 브라우저의 교차 사이트 호출 제한이며, 서버 요청의 인증이나 봇 판별을 대신하지 않는다.
- AI 출력: 구조화된 출력 계약과 서버 검증을 함께 사용한다. 임의 링크, HTML, 잘못된 필드/값은 사용하지 않는다. 회사의 거래 조건은 검증된 로컬 회사 지식으로 안내하며 모델 출력으로 가격·샘플 조건·인증을 바꾸지 않는다. 잘못된 출력/네트워크 장애/사용량 초과는 기본 상담 안내로 이어진다.
- 상담 화면: `site-help.js:53`의 메시지 렌더링은 `textContent`를 사용한다. 외부 링크는 공식 Instagram이나 검증한 WhatsApp 번호로 만들고, 문의 요약은 URL 인코딩한다. 대화 복원 값도 필드/길이를 검사한다. 대화 상태는 해당 브라우저의 sessionStorage에 최대 24개 메시지·4시간 동안 유지된다.
- 개인 정보: Worker의 코드와 Durable Object는 고객 메시지나 원본 IP를 저장·로그하지 않는다. 사용량 제한에는 매일 바뀌는 IP 해시와 카운트만 저장한다. Worker 관측 로그는 비활성화되어 있다. AI 처리 사실은 상담창에 표시한다. AI 제공자의 계정 정책·별도 보관 설정까지 이 코드 검사로 보증하지는 않는다.
- 문의: `apps-script/b2b-lead-automation.gs:546`부터 32KB 본문, 문자열/필드 길이/언어/연락 수단 검사를 적용한다. `:598`의 수식 이스케이프는 모든 문의 저장 셀에 적용한다. 공개 GET은 최소 상태만 반환하고 관리 기능을 실행하지 않는다. 저장 영수증은 중복 알림을 막으며 실패 응답은 내부 예외·시트 ID·알림 본문을 내보내지 않는다.
- 문의 서비스 로그도 번역·알림·원격 응답의 원문 오류를 기록하지 않는다. 분석 이벤트는 별도의 120개 배치/분 캐시 제한을 사용하며, 브라우저에서 제출하는 익명 이벤트를 실제 고객 인증으로 간주하지 않는다.

- 로컬 서버: 뉴스 편집기는 127.0.0.1에만 바인딩하고 Host·Origin·랜덤 세션 토큰을 검사한다. 미리보기는 공개 디렉터리/확장자와 최종 실제 경로를 검사하며 Worker·환경 파일·개인 자료·관리 코드를 내보내지 않는다. 이 로컬 헤더를 운영 홈페이지의 헤더로 간주하지 않는다.
- 저장소: 확인한 Git 추적 텍스트 파일 217개에서 OpenAI/GitHub 토큰·개인 키의 검사 패턴은 발견하지 않았고, 환경 파일·clasp 인증·개인 키가 추적되지 않았다. 패턴 검사로 모든 비밀 값의 부재나 과거 기록을 보증하지는 않는다. 로컬 지식 수집 원문은 무시되는 `output/`에 두고 공개 생성기에 입력하지 않는다.

## 3. 호스팅에서 남는 경계

2026-10-12 `/ko/`, `/ko/contact.html` 실제 응답에서 CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy HTTP 헤더를 확인하지 못했다. 현재 메타 CSP와 referrer 메타는 유지된다. `frame-ancestors`는 메타 CSP에서 작동하지 않으므로 클릭재킹 헤더 방어가 완료되었다고 표현하지 않는다.

GitHub Pages 저장소 파일만으로 HTTP 헤더를 추가할 수 없다. 실제 도메인 앞의 CDN/호스팅 계층에서 헤더를 설정하려면 별도 도메인 연결·라우팅 권한과 검증이 필요하다. 이번 점검에서 DNS·라우팅을 임의로 바꾸거나 비용이 발생하는 플랜을 등록하지 않는다. 강한 봇 판별도 서버 검증 가능한 챌린지/게이트웨이 등 별도 운영 구성이 필요하며, CORS·허니팟·일일 예산을 봇 인증으로 설명하지 않는다.

참조: [CSP frame-ancestors의 메타 제한](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors), [Apps Script 배포](https://developers.google.com/apps-script/concepts/deployments).

## 7. 서버 봇 검증 추가와 운영 확인 · 2026-10-13

대표님의 최신 지시에 따라 Cafe24 로그인, 도메인 등록기관 설정, DNS·네임서버 변경은 진행하지 않았다. 이번 후속 작업은 기존 GitHub Pages와 서버 주소를 유지하면서 문의와 AI의 직접 요청을 보호하는 범위다. 앞의 1~6절은 2026-10-12 점검 당시 기록이며, 아래 내용이 현재 변경 사항이다.

### 적용한 보호

- AI와 문의에 Turnstile 서버 검증을 추가했다. 성공 여부, 정확한 hostname, 용도별 action(`mokda_chat`, `mokda_inquiry`)을 확인한다. 없는·위조된·만료된·재사용된 토큰이나 잘못된 host/action은 사용량 예약·모델 호출·번역·저장·알림 전에 거절한다. 검증 서비스 실패나 비밀값 누락도 검증을 생략하지 않고 요청을 처리하지 않는다.
- 검증 비밀값은 Worker Secret과 기존 Apps Script 비공개 속성에 저장했다. 홈페이지에는 공개 sitekey만 있으며 토큰을 브라우저 저장소에 보관하지 않는다. 기존 서버 연결 속성도 보존했다.
- Cloudflare 검증 스크립트는 실제 AI 질문이나 문의 제출 시에만 불러온다. 일반 페이지 방문과 기본 상담 안내에는 추가로 불러오지 않는다. 모바일의 네이티브 상담 dialog 안에 검증 UI가 표시되도록 했으며, 중단·제한 시간·위젯 정리 경로도 검사했다. 실패한 문의는 입력을 보존하고 AI는 기존 기본 안내로 이어진다.
- 현재 meta CSP의 `frame-src`는 기존 `'none'`에서 검증용 `https://challenges.cloudflare.com`만 허용하도록 변경했다. script/connect도 같은 정확한 출처만 추가했다. 기존 해시 기반 스크립트 제한, `object-src 'none'`, `form-action 'none'`, `script-src-attr 'none'` 및 스크립트의 `unsafe-inline`·`unsafe-eval` 금지는 유지한다.
- 기존 AI 일일 80회·방문 IP별 분당 3회/일일 20회와 문의 한국 시간 일일 80건 제한은 유지한다. AI의 UTC 자정 변경을 통과하는 테스트 시간을 고정하고 실제 자정 초기화 검사도 추가했다. 토큰 실패는 모델 호출을 하지 않으며, 이후 단계에서 실패한 모델 요청이 예산을 소비하는 기존 원칙은 유지한다.

### 이번 범위에서 남는 경계

Cloudflare 무료 도메인 영역과 HTTPS·응답 헤더 설정을 준비했으나, 기존 네임서버를 유지하므로 홈페이지 트래픽에는 적용되지 않는다. 홈페이지 전체 WAF, HTTP 보안 헤더, 클릭재킹 헤더 방어가 활성화되었다고 표현하지 않는다. 계정 인증수단도 변경하지 않았다.

문의·AI 검증은 해당 서버의 모델 호출·고객 저장·알림에 앞서 요청을 거절하는 보호다. 정적 홈페이지 전체나 Google 계정의 서비스 할당량에 대한 DDoS 방어를 보증하지 않는다. 익명 분석 이벤트의 기존 제한은 유지하지만 분석 제출자를 인증하는 방식으로 바꾸지는 않았다. 5절에 기록한 개발 도구 취약점 경계도 그대로 남는다.
